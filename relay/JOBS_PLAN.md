# 화면을 꺼도 이어지는 AI 작업

## 진행 단계

| 단계 | 범위 | 완료 기준 | 상태 |
|---|---|---|---|
| 1. 서버 작업 기반 | 영구 접수·예약 실행·상태·결과 조회, 중복 접수 방지 | 접수 HTTP 요청과 독립된 실행, 재기동 후 조회, 계정 격리 | v6.88 구현 |
| 2. AI 실행 연결 | Gemini 문서·검사 및 Gemini/OpenAI 이미지 어댑터 | 모델·생각 깊이·키 설정 보존, 이미지 결과 서버 보관 | v6.89 구현 |
| 3. 화면 복구 | 진행 목록, 복귀·새로고침·탭 재실행 후 결과 미리보기·반영 | 브라우저 새로고침·탭 종료 뒤 같은 결과 회수, 중복 요청 없음 | v6.90 구현 |
| 4. 문서 전체 과정 | 생성 → 검사 → 필요 시 자동 수정 → 저장의 서버 실행 | 브라우저가 없어도 전체 단계 완료, 수정·삭제 충돌 처리 | 예정 |

v6.88에서 서버 기반을 추가했고, v6.89에서 앱의 Gemini 문서·검사 호출과 Gemini/OpenAI 이미지·단편 삽화를 연결했다.
**로그인하고 서버 AI 실행을 켜면, 서버에 접수된 한 호출은 화면 잠금·탭 전환으로 브라우저 연결이 끊겨도 실행된다. 살아 있는 탭으로 돌아오면 같은 작업 번호로 결과를 받는다.**
v6.90은 새로고침·탭 재생성 뒤 **AI 작업** 화면에서 진행 상태와 결과를 복구한다. 브라우저가 없는 동안 생성 → 검사 → 수정 → 저장을 모두 마치는 것은 4단계다.

## 3단계 사용 방법과 범위

1. 작업을 접수한 계정으로 로그인한다. 접수 정보가 이 브라우저에 있으면 새로고침 뒤 복구할 작업 화면을 자동으로 연다. 다른 경우에는 사이드바 **도구 → AI 작업**을 연다.
2. 진행 상태는 화면이 보이는 동안 주기적으로 갱신한다. 로컬 접수 기록이 없어도 서버 목록의 복구 대상 정보를 가져온다. 과거 작업을 조회하는 데 AI 키를 다시 보낼 필요는 없다.
3. **결과 보기**에서 문서 본문·검사 지적·이미지·단편을 확인한다. 이미 캐시한 결과는 서버 연결이 끊겨도 열 수 있다.
4. **문서로 저장 (자동 검사 전)**, **검사 결과 반영**, **이 이미지 적용**, **이 단편 보관**으로 직접 반영한다. 복구 자체는 AI를 다시 부르지 않는다. 복구 문서에 자동 검사·자동 교정을 추가 실행하지 않는다.
5. 대조·읽기 검사는 같은 묶음의 완료 결과를 합치고 현재 자료로 코드 검사를 더한다. 한 검사가 아직 진행 중이면 기다리도록 안내한다. 원래 검사 이후에 생긴 더 최근 검사 결과를 덮어쓰지 않는다.
6. 원본 문서·참고 문서·세계관 설정이 바뀌었으면 반영을 거절하고 결과를 보관한다. 삭제된 세계관을 복구 결과 때문에 다시 만들지 않는다. 이미지는 본문·기존 이미지·참고 프로필, 단편 삽화는 대상 단편까지 대조한다.
7. 반영 직전에도 IndexedDB 트랜잭션에서 원본과 로그인 상태를 다시 확인하고 세계관·문서를 함께 저장한다. localStorage만 쓰는 환경에서는 안전한 반영 대신 내려받기를 안내한다.
8. **결과 내려받기**로 원본 결과를 JSON으로 보관할 수 있다. 진행 중인 작업은 새 탭에서도 중단할 수 있다. 완료 항목은 **복구 목록에서 닫기**로 정리하며 전체 기록에서는 다시 볼 수 있다.
9. 로그아웃·계정·서버 변경 시 목록과 미리보기를 비운다. 확인한 작업은 서버에도 표시해 다른 탭·기기에서 미확인 작업으로 계속 나타나지 않게 한다.

접수되지 않았거나 서버에서 만료된 번호를 발견해도 새 요청을 자동으로 만들지 않는다.
v6.89 이전 작업처럼 원본 대조 정보가 없는 기록은 미리보기·내려받기만 제공한다. 문단 수정·교정 등 아직 전용 적용 동작을 연결하지 않은 결과도 내려받을 수 있다.
실제 iPhone의 절전·운영체제 메모리 종료는 별도 기기 확인이 필요하다. 자동 테스트는 브라우저 새로고침·탭 종료·새 탭·통신 중단·오프라인 캐시로 검증한다.

## 2단계 사용 방법

1. **AI 연결 설정 → 계정**에서 기존 서버 계정으로 로그인한다.
2. **화면을 꺼도 AI 요청 계속하기 → 로그인한 동안 AI 요청을 서버에서 실행**을 켜고 저장한다. 기본값은 켜짐이다.
3. 중계 서버 Gemini 연결은 그대로 서버 키를 쓴다. 개인 Gemini 또는 OpenAI 키를 쓰려면 **내 Gemini·OpenAI 키도 서버 작업에 사용하도록 허용**을 직접 켜고 저장한다. 기본값은 꺼짐이다.
4. 개인 키 허용은 선택한 서버 주소에만 적용한다. 주소 변경·다른 서버 초대 링크에서는 해제된다. 키 연결 방식·모델·생각 깊이·이미지 비율·품질은 바꾸지 않는다.
5. 로그인하지 않았거나 서버 AI 실행을 끄면 기존 직접/중계 호출을 쓴다. 개인 키를 허용하지 않으면 개인 키 호출은 직접 연결을 유지한다.
6. 서버 호출은 중간 글자를 스트리밍하지 않고 완료 결과를 한 번에 받는다. 접수 뒤 서버 오류가 나도 직접 호출로 몰래 전환하거나 새 작업 번호로 재시도하지 않는다.

앱은 접수 전 작업 번호·계정·서버·대상 문서 정보를 로컬에 저장한다. 같은 탭에서 통신이 끊기면 해당 번호를 조회하며,
접수 성공 여부가 불명확하고 서버에 번호가 없을 때만 **같은 번호·같은 내용**으로 접수한다.
완료 결과는 브라우저 저장소에도 보관하고, 로컬 보관 성공 후에만 서버에 수신 확인(`ack`)을 보낸다.
로컬 결과 캐시는 최근 20건·약 40MiB까지이며, 실패하면 서버 결과를 수신 처리하지 않는다. 캐시한 결과는 AI 작업 화면에서 열고 적용한다.
기존 문서·이미지 저장과 적용 전 수정 충돌 검사는 유지한다.

## 1단계 설계

- 기존 Worker와 D1 계정 인증을 유지하고 SQLite Durable Object `AI_JOBS`를 추가한다.
- 계정마다 하나의 영구 큐를 사용한다. 한 번에 한 작업씩 실행한다.
- 접수 시 요청·메타데이터·alarm 예약을 하나의 저장 트랜잭션으로 기록한다. 접수 응답 뒤 `waitUntil()`에 의존하지 않는다.
- alarm에서 Gemini `generateContent` 또는 OpenAI `images/generations`·`images/edits`를 호출한다. 클라이언트 HTTP 연결이 없어도 실행된다. 참고 이미지는 Gemini inlineData 또는 OpenAI multipart로 전달한다.
- 작업 번호는 클라이언트가 최초 전송 **전에** 생성·보관한다. 응답이 유실되면 같은 번호와 같은 요청으로 다시 접수하거나 조회한다.
- 같은 번호·같은 요청은 기존 작업을 반환한다. 같은 번호·다른 요청은 409다. 모델과 입력의 직렬화 결과를 비교하므로 재접수 시 원래 요청을 그대로 사용한다.
- 작업 결과를 확인할 수 없는 네트워크 오류·서버 재기동 시 `interrupted`로 남긴다. 자동으로 AI 요청을 다시 보내지 않는다. 서버가 재기동한 뒤 완료 여부가 불명인 작업을 정확히 이어 실행하는 것은 제공자 측 조회 기능 없이는 보장할 수 없다.
- `cancel`은 상태를 중단으로 바꾸고 가능한 경우 진행 중인 fetch를 abort한다. 이미 제공자에서 시작된 생성·과금의 취소를 보장하지 않는다.
- 서버의 결과 보관과 문서 반영은 별개다. 2단계는 살아 있는 탭의 기존 처리 과정으로 결과를 돌려준다. 서버 자체는 세계관·문서를 수정하거나 이미지를 자동 적용하지 않는다.
- 3단계부터 요청에 제한된 `meta`를 저장한다. 대상 세계관·문서·단편, 작업 묶음, 원본 대조용 해시만 포함하고 API 키·입력 프롬프트는 넣지 않는다. 이미 수신한 결과와 아직 반영하지 않은 결과를 구분한다.

### 보관과 제한

- 번호·입력 지문은 종료 후 24시간 보관한다. 못 받은 결과는 만료 전까지 유지한다. 받은 결과는 서버에서 최근 최대 20건까지 보관하며, 더 오래된 받은 결과를 지워도 번호·입력 지문은 남긴다.
- 계정당 미수신 최대 20건, 진행·대기 합계 최대 8건, 24시간 내 번호 이력 최대 500건이다. 완료 기록은 명시적으로 삭제할 수도 있다. 큰 목록도 KV 조각으로 저장한다.
- 입력 본문 최대 2MiB, 텍스트 응답 최대 4MiB, 이미지 응답 최대 20MiB다. 실행 시간은 텍스트 10분, OpenAI 이미지 5분, Gemini 이미지 3분이며 큐 대기는 제외한다.
- 긴 입력·결과는 KV 값 크기 제한에 맞게 나누어 트랜잭션으로 저장한다. 종료 후에는 입력 본문을 지운다.
- 공유 키와 접속 암호는 작업 데이터에 저장하지 않는다. 허용한 개인 키만 입력과 분리된 비공개 저장 키에 대기·실행 동안 임시 보관한다. Cloudflare 저장소의 기본 저장 시 암호화를 사용하며 별도 애플리케이션 암호화는 추가하지 않았다. 서버 관리자는 작업 동안의 개인 키에 접근할 수 있으므로 신뢰하는 서버에만 허용한다.
- 개인 키는 성공·실패·통신 오류·취소·재기동 복구 때 지우고, 실행 중 예기치 않은 종료에 대비한 정리 alarm도 예약한다. 개인 키가 없어진 작업을 공유 키로 대신 실행하지 않는다. 요청 URL·조회 응답·제공자 오류 원문·백업·세계관 동기화에 키를 넣지 않는다.
- 삭제·만료 후에는 해당 작업 번호에 대한 중복 방지 기록도 사라진다. 번호를 재사용하지 않는다.
- 새 Durable Object에는 미국 동부 위치 힌트를 준다. 기존 Worker의 placement와 별개이며 국가 고정 보장은 아니다. 실제 배포 후 Gemini 지역 제한 여부를 확인한다.

## API

공통: 기존 `/api/login` 또는 `/api/signup`에서 받은 `Authorization: Bearer <token>`과 허용된 `Origin`이 필요하다.
서버 공유 키로 접수할 때는 `X-WW-Pass`에 기존 중계 서버 접속 암호도 필요하다. 개인 키 요청은 로그인과 아래 `credential`을 사용한다. 브라우저가 인증 헤더를 후속 조회에 붙일 수 있어야 한다.

| 메서드·경로 | 기능 |
|---|---|
| `POST /api/jobs` | 새 작업 접수(202), 동일 작업 재조회(200) |
| `GET /api/jobs` | 이 계정의 작업 메타데이터 목록(최근순, 결과 본문 제외) |
| `GET /api/jobs/:id` | 상태와 완료 시 Gemini 원본 JSON `result` 조회 |
| `POST /api/jobs/:id/cancel` | 대기·실행 중 작업 중단 |
| `POST /api/jobs/:id/ack` | 로컬에 결과를 보관한 뒤 수신 확인. 번호는 유지 |
| `POST /api/jobs/:id/resolve` | 종료된 결과를 반영·확인했음을 기록. 번호와 원문은 유지 |
| `POST /api/jobs/:id/forget` | 종료된 기록과 결과 삭제 |

접수 본문:

```json
{
  "id": "7c63cb28-753e-4cbd-9096-d405ff24c572",
  "type": "gemini.generate",
  "model": "gemini-3.8-flash",
  "input": {
    "contents": [{ "role": "user", "parts": [{ "text": "요청할 내용" }] }],
    "generationConfig": { "responseMimeType": "application/json" }
  }
}
```

`id`에는 `crypto.randomUUID()`처럼 영문·숫자·`_`·`-`로 된 16~80자 문자열을 쓴다. `model`은 앱에 설정한 실제 모델로 바꾼다.
`gemini.generate`는 텍스트 `contents`, `generationConfig`, 텍스트 `systemInstruction`, `safetySettings`를 허용한다.
`gemini.image`는 같은 구조에 PNG/JPEG/WebP `inlineData`와 IMAGE 모달리티를 허용한다. 외부 파일·도구 호출은 지원하지 않는다.
`openai.image`는 `input: {prompt, size, quality, reference?: {mimeType, data}}`를 사용하며, 서버가 PNG 한 장으로 고정한다.
개인 키 요청은 접수 본문에 `credential: {type: "personal", key: "개인 API 키"}`를 추가한다. OpenAI는 개인 키가 필수다.
참고 이미지는 base64 최대 1.5MiB이며, OpenAI 크기·품질은 기존 앱의 선택지를 따른다.
선택적인 `meta`에는 작업 종류·대상·원본 해시 등의 정해진 필드만 허용하며 총 4,096자 이하다. 임의 키·인증 값은 받지 않는다.

응답에는 `job.id`, `job.status`, `createdAt`, 실행 시 `startedAt`, 종료 시 `finishedAt`·`expiresAt`이 포함된다.
상태는 `queued`, `running`, `succeeded`, `failed`, `cancelled`, `interrupted`다. 실패 시 `job.error`가 있다.
원래 입력·키·내부 저장 키는 조회 응답에 포함하지 않는다.

## 배포와 검증

- `wrangler.toml`의 `AI_JOBS` 바인딩과 `v1-ai-jobs` SQLite migration을 함께 배포한다. D1 기존 테이블은 변경하지 않는다.
- 기존처럼 `relay/` 변경을 `main`에 반영하면 연결된 Workers Builds가 배포한다. 실제 성공 여부는 GitHub/Cloudflare 빌드 상태를 확인한다.
- 배포 후 루트 진단의 `jobsConfigured: true`, `jobsVersion: 3`으로 3단계 서버 배포를 확인한다. 앱의 로그인·개인 키 허용 여부에 따라 실제 호출 경로가 달라진다.
- 기존 계정으로 테스트 작업 접수 → 원래 연결 종료 → 잠시 뒤 같은 번호로 조회 → 다른 계정에서 조회 불가를 확인한다. 실제 AI를 사용하는 이 확인은 제공자 API 사용료가 발생한다.
- 단위·회귀 테스트: `node tests/run-all.js` 또는 `node tests/run-all.js job-recovery relay-jobs relay-providers server-ai relay-storage`.
- 배포 번들 검사: `cd relay && npx wrangler deploy --dry-run`.
- 구현 중에는 실제 workerd 엔진과 SQLite Durable Object·D1에서 alarm 실행·조회도 확인했다. 제공자 응답을 대체해 유료 AI 호출은 하지 않았다.

## 다음 단계에서 유지할 조건

1. 개인 키의 서버별 허용과 제공자별 키 분리를 계속 유지한다.
2. 이미지 원본 결과·로컬 캐시·미리보기·문서 적용의 수신 상태를 구분한다.
3. 3단계의 원본 대조와 중복 반영 방지를 전체 서버 과정에서도 유지한다.
4. 작업 중 수정·삭제된 문서와 세계관은 자동으로 덮어쓰거나 다시 만들지 않는다. 결과를 별도로 보관해 사용자가 회수할 수 있게 한다.
5. 문서 단계 진행과 결과 저장은 영구 기록을 기준으로 이어 간다. 단일 AI 호출의 서버 실행만으로 전체 문서 과정이 백그라운드에서 끝난다고 표시하지 않는다.
6. 완료 알림이 필요하면 별도 알림 기능으로 다룬다. 브라우저를 닫아도 서버 실행은 가능하지만 닫힌 화면의 진행 표시 갱신은 불가능하다.
