# 화면을 꺼도 이어지는 AI 작업

## 진행 단계

| 단계 | 범위 | 완료 기준 | 상태 |
|---|---|---|---|
| 1. 서버 작업 기반 | 영구 접수·예약 실행·상태·결과 조회, 중복 접수 방지 | 접수 HTTP 요청과 독립된 실행, 재기동 후 조회, 계정 격리 | v6.88 구현 |
| 2. AI 실행 연결 | Gemini 문서·검사 및 Gemini/OpenAI 이미지 어댑터 | 모델·생각 깊이·키 설정 보존, 이미지 결과 서버 보관 | 예정 |
| 3. 화면 복구 | 접수 전 작업 번호 저장, 진행 목록, 복귀·새로고침 시 복원 | 실제 휴대폰 잠금·탭 종료 후 결과 회수, 중복 요청 없음 | 예정 |
| 4. 문서 전체 과정 | 생성 → 검사 → 필요 시 자동 수정 → 저장의 서버 실행 | 브라우저가 없어도 전체 단계 완료, 수정·삭제 충돌 처리 | 예정 |

1단계는 서버 기반을 추가한다. **현재 앱의 AI 호출 경로는 바꾸지 않으므로 아직 휴대폰 연결 끊김 문제를 해결한 버전은 아니다.**
서버 기반 검증용으로 Gemini 텍스트 단일 호출을 실행할 수 있다. 문서 조립·검사·저장과 이미지는 연결하지 않았다.

## 1단계 설계

- 기존 Worker와 D1 계정 인증을 유지하고 SQLite Durable Object `AI_JOBS`를 추가한다.
- 계정마다 하나의 영구 큐를 사용한다. 한 번에 한 작업씩 실행한다.
- 접수 시 요청·메타데이터·alarm 예약을 하나의 저장 트랜잭션으로 기록한다. 접수 응답 뒤 `waitUntil()`에 의존하지 않는다.
- alarm에서 Gemini `generateContent`를 호출한다. 클라이언트 HTTP 연결이 없어도 실행된다. 중간 스트리밍은 후속 단계의 범위다.
- 작업 번호는 클라이언트가 최초 전송 **전에** 생성·보관한다. 응답이 유실되면 같은 번호와 같은 요청으로 다시 접수하거나 조회한다.
- 같은 번호·같은 요청은 기존 작업을 반환한다. 같은 번호·다른 요청은 409다. 모델과 입력의 직렬화 결과를 비교하므로 재접수 시 원래 요청을 그대로 사용한다.
- 작업 결과를 확인할 수 없는 네트워크 오류·서버 재기동 시 `interrupted`로 남긴다. 자동으로 AI 요청을 다시 보내지 않는다. 서버가 재기동한 뒤 완료 여부가 불명인 작업을 정확히 이어 실행하는 것은 제공자 측 조회 기능 없이는 보장할 수 없다.
- `cancel`은 상태를 중단으로 바꾸고 가능한 경우 진행 중인 fetch를 abort한다. 이미 제공자에서 시작된 생성·과금의 취소를 보장하지 않는다.
- 결과 확인과 문서 반영은 별개다. 아직 세계관·문서를 수정하거나 결과를 자동 적용하지 않는다.

### 보관과 제한

- 완료·실패·중단 결과는 종료 후 24시간 보관한다. alarm과 API 접근 시 만료 데이터를 정리한다.
- 계정당 최대 20개 기록, 진행·대기 합계 최대 8개다. 완료 기록은 명시적으로 삭제할 수 있다.
- 입력 본문 최대 2MiB, 생성 응답 최대 4MiB, 실행 최대 10분이다.
- 긴 입력·결과는 KV 값 크기 제한에 맞게 나누어 트랜잭션으로 저장한다. 종료 후에는 입력 본문을 지운다.
- API 키·접속 암호는 작업 데이터에 저장하지 않는다. 1단계는 서버의 `GEMINI_KEY`만 쓴다. 개인 API 키·OpenAI는 후속 단계에서 다룬다.
- 삭제·만료 후에는 해당 작업 번호에 대한 중복 방지 기록도 사라진다. 번호를 재사용하지 않는다.
- 새 Durable Object에는 미국 동부 위치 힌트를 준다. 기존 Worker의 placement와 별개이며 국가 고정 보장은 아니다. 실제 배포 후 Gemini 지역 제한 여부를 확인한다.

## API

공통: 기존 `/api/login` 또는 `/api/signup`에서 받은 `Authorization: Bearer <token>`과 허용된 `Origin`이 필요하다.
작업을 새로 접수할 때는 `X-WW-Pass`에 기존 중계 서버 접속 암호도 필요하다. 브라우저가 인증 헤더를 후속 조회에 붙일 수 있어야 한다.

| 메서드·경로 | 기능 |
|---|---|
| `POST /api/jobs` | 새 작업 접수(202), 동일 작업 재조회(200) |
| `GET /api/jobs` | 이 계정의 작업 메타데이터 목록(최근순, 결과 본문 제외) |
| `GET /api/jobs/:id` | 상태와 완료 시 Gemini 원본 JSON `result` 조회 |
| `POST /api/jobs/:id/cancel` | 대기·실행 중 작업 중단 |
| `POST /api/jobs/:id/forget` | 종료된 기록과 결과 삭제 |

접수 본문:

```json
{
  "id": "7c63cb28-753e-4cbd-9096-d405ff24c572",
  "type": "gemini.generate",
  "model": "gemini-3.8-flash",
  "input": {
    "contents": [{ "role": "user", "parts": [{ "text": "요청할 내용" }] }],
    "generationConfig": { "responseMimeType": "application/json" }
  }
}
```

`id`에는 `crypto.randomUUID()`처럼 영문·숫자·`_`·`-`로 된 16~80자 문자열을 쓴다. `model`은 앱에 설정한 실제 모델로 바꾼다.
1단계는 텍스트 `contents`, `generationConfig`, 텍스트 `systemInstruction`, `safetySettings`를 허용한다.
이미지·외부 파일·도구 호출은 허용하지 않는다.

응답에는 `job.id`, `job.status`, `createdAt`, 실행 시 `startedAt`, 종료 시 `finishedAt`·`expiresAt`이 포함된다.
상태는 `queued`, `running`, `succeeded`, `failed`, `cancelled`, `interrupted`다. 실패 시 `job.error`가 있다.
원래 입력·키·내부 저장 키는 조회 응답에 포함하지 않는다.

## 배포와 검증

- `wrangler.toml`의 `AI_JOBS` 바인딩과 `v1-ai-jobs` SQLite migration을 함께 배포한다. D1 기존 테이블은 변경하지 않는다.
- 기존처럼 `relay/` 변경을 `main`에 반영하면 연결된 Workers Builds가 배포한다. 실제 성공 여부는 GitHub/Cloudflare 빌드 상태를 확인한다.
- 배포 후 루트 진단의 `jobsConfigured: true`로 바인딩 여부를 확인한다. 이는 앱이 새 호출 경로를 사용한다는 뜻은 아니다.
- 기존 계정으로 테스트 작업 접수 → 원래 연결 종료 → 잠시 뒤 같은 번호로 조회 → 다른 계정에서 조회 불가를 확인한다. 실제 AI를 사용하는 이 확인은 제공자 API 사용료가 발생한다.
- 단위·회귀 테스트: `node tests/run-all.js` 또는 `node tests/run-all.js relay-jobs relay-storage`.
- 배포 번들 검사: `cd relay && npx wrangler deploy --dry-run`.
- 구현 중에는 실제 workerd 엔진과 SQLite Durable Object·D1에서 alarm 실행·조회도 확인했다. 제공자 응답을 대체해 유료 AI 호출은 하지 않았다.

## 다음 단계에서 유지할 조건

1. 개인 키 연결을 서버 공유 키로 몰래 바꾸지 않는다. 제공자별 키 취급과 서버 보관 범위를 명확하게 결정한다.
2. Gemini/OpenAI 이미지 결과는 크기·참고 이미지 업로드·미리보기 보관을 고려해 별도 어댑터와 저장소를 둔다.
3. 탭 복귀뿐 아니라 앱 새로고침·탭 재생성 후에도 접수한 작업 번호와 대상 세계관·문서를 복원한다.
4. 작업 중 수정·삭제된 문서와 세계관은 자동으로 덮어쓰거나 다시 만들지 않는다. 결과를 별도로 보관해 사용자가 회수할 수 있게 한다.
5. 문서 단계 진행과 결과 저장은 영구 기록을 기준으로 이어 간다. 단일 AI 호출의 서버 실행만으로 전체 문서 과정이 백그라운드에서 끝난다고 표시하지 않는다.
6. 완료 알림이 필요하면 별도 알림 기능으로 다룬다. 브라우저를 닫아도 서버 실행은 가능하지만 닫힌 화면의 진행 표시 갱신은 불가능하다.
